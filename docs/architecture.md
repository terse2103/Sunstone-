## 1. Overview

PlacementIQ is an AI-powered placement readiness intelligence suite for Sunstone Edtech students and placement counselors. It is a two-tier web application with three logical surfaces:

- **Student view (Pillars A + B):** real-time readiness score, ELQD skill radar, AI-generated top 3 priority gaps
- **Counselor view (Pillar C):** at-risk student panel with AI-generated intervention briefs
- **Evals view:** read-only results of the three eval suites required by the spec

The system follows a strict separation of concerns: **numerical decisions are made by deterministic pure functions, narrative outputs are generated by a live LLM**. This keeps evals stable, outputs auditable, and the demo robust.

### Core principles

1. **Numbers are deterministic, language is LLM-generated.** Scores, gap rankings, and at-risk flags are pure functions over student data and recruiter benchmarks — fully reproducible. The Claude API only writes explanatory text around those numbers. As a result, the three evals all test deterministic logic, not LLM behavior — making them stable and meaningful.

2. **Evals are offline + read-only at runtime.** `evals/run.py` runs golden datasets through the same `core/` modules the app uses, writes results to `evals/results/`. The app's `/evals` page just reads and renders those files. No live eval execution from the browser.

3. **Every output cites its input signals.** Score breakdowns, gap rationales, and intervention briefs all surface the data they were computed from — required by the spec's explainability constraint.

## 4. Backend Architecture

### 4.1 Layer structure

```
backend/app/
├── main.py                 # FastAPI app, CORS, router mounting, lifespan (seed load)
├── routes/                 # Thin HTTP handlers
│   ├── auth.py
│   ├── student.py
│   ├── counselor.py
│   └── evals.py
├── core/                   # Pure functions — no I/O, no LLM, fully unit-testable
│   ├── scoring.py
│   ├── gaps.py
│   ├── at_risk.py
│   └── benchmarks.py
├── llm/                    # Claude API wrapper + prompts
│   ├── client.py
│   └── prompts.py
├── data/                   # Seed data + loader
│   ├── students.json
│   ├── benchmarks.json
│   └── seed.py
└── models/                 # Pydantic schemas (typed API contracts)
```

**Dependency rule:** `routes/` may import from `core/`, `llm/`, `data/`, `models/`. `core/` imports nothing else from the app — it is pure. `llm/` imports only `models/`. This makes the deterministic engine and the LLM swappable independently.

### 4.2 `core/` — the deterministic engine

The heart of the system. No network, no I/O, no LLM. Everything here is testable in isolation, and the evals exercise these modules directly.

**`benchmarks.py`**
- Loads `benchmarks.json` once into a module-level dict
- Exposes `get_track(name) -> TrackBenchmark`
- 3 hardcoded tracks: `BFSI`, `Analytics`, `Digital Marketing`
- Each track holds: ELQD dimension weights (sum to 1.0) and per-sub-skill benchmarks (0–100)

**`scoring.py`**
- `compute_dimension_score(assessments, attendance, time_on_task) -> float`
  - Weighted blend: **60% assessments** (average across the dimension's sub-skills) + **20% attendance** + **20% time-on-task**
- `compute_readiness(student, track) -> ReadinessResult`
  - Overall = weighted sum of 4 dimension scores using track weights
  - Returns overall + per-dimension breakdown + the raw input signals (for the explainability requirement)

**`gaps.py`**
- `compute_gaps(student, track) -> list[Gap]`
  - For each sub-skill in the track: `gap_size = benchmark - student_score`; keep only positives
- `top_n_gaps(student, track, n=3) -> list[Gap]`
  - Sorts by `priority_score = gap_size × dimension_weight`
  - Each `Gap` carries: sub-skill name, parent dimension, gap_size, rank, and the input signals used (assessment scores, JD frequency) — so the LLM rationale can cite them

**`at_risk.py`**
- `assess_at_risk(student, track) -> AtRiskAssessment`
- Inputs: current readiness score, trajectory (linear regression slope across last 3 assessment cycles), recent attendance, days-to-placement
- Rule: flagged if `readiness < 55` **and** `trajectory_slope ≤ 0` **and** `days_to_placement >= 60`
- The 60-day floor enforces the spec's "intervention must be meaningful, not cosmetic" constraint
- Risk level: `high` if readiness < 45, `medium` if 45–55, `low` otherwise
- Returns risk level, primary gap driving risk, and contributing signals (list of strings the LLM brief can use)

### 4.3 Career track benchmarks

3 hardcoded tracks: **BFSI**, **Analytics**, **Digital Marketing**. Each defines dimension weights and sub-skill benchmarks. Example:

```json
{
  "Analytics": {
    "weights": { "E": 0.15, "L": 0.20, "Q": 0.35, "D": 0.30 },
    "subskills": {
      "business_communication": { "dimension": "E", "benchmark": 70 },
      "presentation":           { "dimension": "E", "benchmark": 65 },
      "logical_reasoning":      { "dimension": "L", "benchmark": 75 },
      "data_interpretation":    { "dimension": "Q", "benchmark": 85 },
      "quant_aptitude":         { "dimension": "Q", "benchmark": 75 },
      "sql_basics":             { "dimension": "D", "benchmark": 80 },
      "stats_fundamentals":     { "dimension": "D", "benchmark": 75 },
      "excel_modelling":        { "dimension": "D", "benchmark": 70 }
    },
    "jd_frequency": {
      "data_interpretation": 0.73,
      "sql_basics": 0.68,
      "business_communication": 0.61
    }
  }
}
```

`jd_frequency` is the share of recruiter JDs in this track that demand the sub-skill — used in LLM rationale prompts (e.g., "Required in 73% of Analytics JDs").

### 4.4 `llm/` — the narrative layer

Thin and well-bounded. Only two LLM tasks exist in the system.

**`prompts.py`** — two prompt templates as constants:

- `GAP_RATIONALE_PROMPT` — given a `Gap` + student context, produce a single sentence explaining why this gap matters, citing one specific input signal (e.g., JD frequency, mock interview rejection reason)
- `INTERVENTION_BRIEF_PROMPT` — given `AtRiskAssessment` + recent signals, produce a 3-line counselor brief in the exact format from the spec: Score → Primary gap + risk → Recent signal + recommended action

**`client.py`**

- `AnthropicClient` wraps the Anthropic Python SDK, reads `ANTHROPIC_API_KEY` from env
- Model: `claude-haiku-4-5-20251001` (fast, cheap, sufficient for 1–3 lines)
- **In-memory cache** keyed on `(function_name, input_hash)` — same inputs return cached output. Drastically reduces cost during demo and reviewer exploration
- **Failure mode:** if the API call fails (network, missing key, rate limit), the wrapper returns a deterministic templated fallback string. The demo never breaks because of LLM issues

### 4.5 `routes/` — thin HTTP layer

Routes validate input, call core + llm modules, return Pydantic models. All response shapes are typed and appear in FastAPI's auto-generated OpenAPI docs at `/docs`.

| Method | Path | Returns | Composition |
|---|---|---|---|
| POST | `/api/auth/login` | `{role, student_id?}` | Mock — no token; frontend stores role/id in context |
| GET | `/api/students` | list of seeded students | Powers the login picker |
| GET | `/api/students/{id}` | full `Student` profile | From in-memory seed |
| GET | `/api/students/{id}/readiness` | `ReadinessResult` | `scoring.compute_readiness()` |
| GET | `/api/students/{id}/gaps?n=3` | list of `Gap` w/ rationale | `gaps.top_n_gaps()` + `llm.gap_rationale()` per gap (parallel) |
| GET | `/api/counselor/at-risk` | list of `AtRiskStudent` | iterate seed → `at_risk.assess()` → filter flagged |
| GET | `/api/counselor/students/{id}/brief` | `InterventionBrief` | `at_risk.assess()` + `llm.intervention_brief()` |
| POST | `/api/counselor/students/{id}/action` | `204` | In-memory set, lost on restart (acceptable for prototype) |
| GET | `/api/evals/results` | latest results JSON | Reads `evals/results/report.json` from disk |
| GET | `/healthz` | `{status: "ok"}` | Hosting health check |

### 4.6 Request flow — student loads dashboard

1. Browser hits `/student/STU_001` → React fetches:
   - `GET /api/students/STU_001/readiness` → seed lookup → `core.scoring.compute_readiness()` → returns in ms (no LLM)
   - `GET /api/students/STU_001/gaps?n=3` → `core.gaps.top_n_gaps()` → for each gap, `llm.gap_rationale()` — 3 LLM calls run in parallel via `asyncio.gather()`
2. UI renders deterministic score and radar immediately; rationales stream in as the LLM calls complete
3. On subsequent loads of the same student, cached rationales return in ms

## 5. Frontend Architecture

### 5.1 Pages and routes

| Route | Page | Renders |
|---|---|---|
| `/` | LoginPage | Role chooser + student picker (if Student) |
| `/student/:id` | StudentDashboard | Readiness score card, ELQD radar, top 3 gaps |
| `/counselor` | CounselorDashboard | At-risk student table |
| `/counselor/student/:id` | InterventionDetail | Intervention brief + "mark action taken" |
| `/evals` | EvalsPage | Latest eval results |

Routing: `react-router-dom`. The current user (role + student_id) is held in a React Context populated by `LoginPage` and cleared on a logout button in the header.

### 5.2 Components

- `<ReadinessScoreCard>` — overall score (big number) + per-ELQD breakdown bars
- `<SkillRadarChart>` — Recharts radar with student vs. track benchmark overlaid
- `<TopGapsList>` — 3 gap rows, each showing dimension, gap size, deterministic signal, and the LLM rationale
- `<AtRiskTable>` — sortable list (by risk score), row click → intervention detail
- `<InterventionBriefCard>` — 3-line LLM brief + the contributing signals beneath it + action button
- `<EvalsResultsViewer>` — pass/fail badges per eval, expandable per-test-case details

### 5.3 State management

- **Server state:** TanStack Query for all API responses. Cache, revalidate, suspend.
- **Session state:** React Context for the current user (role + student_id).
- **No global store.** Page-local state with `useState`.

### 5.4 Mobile-first

- Tailwind's mobile breakpoint is the default; desktop expansions use `md:` / `lg:` prefixes
- Student dashboard is single-column on mobile, two-column on desktop
- Radar chart container uses `aspect-square` to scale cleanly across viewports
- Counselor view targets desktop primarily (counselors mostly desktop) but remains usable on mobile

## 7. Evals System

### 7.1 The three evals (from spec)

| Eval | Tests | Dataset | Key Metric | Pass Threshold |
|---|---|---|---|---|
| Score Calibration | `core/scoring.py` | 10 golden profiles w/ outcome labels | Directional accuracy + sensitivity | Score < 50 → "not placed"; Score > 70 → "placed"; 15-pt input change moves overall meaningfully |
| Gap Relevance | `core/gaps.py` | 5 profiles w/ manually-defined top-3 | Precision + ranking accuracy | 3/3 match on ≥4 of 5 profiles; #1 gap always correct |
| Early Warning | `core/at_risk.py` | 8 trajectories (4 at-risk, 4 on-track) | Recall + false positive rate | Recall = 4/4 at-risk flagged; ≤1 false positive |

### 7.2 `evals/` structure

```
evals/
├── datasets/
│   ├── score_calibration.json   # 10 profiles with expected outcome buckets
│   ├── gap_relevance.json       # 5 profiles with manually-set top-3 gaps
│   └── early_warning.json       # 8 trajectories with at-risk ground truth
├── run.py                       # Runs all 3, writes results
├── results/
│   ├── report.json              # Machine-readable, consumed by /api/evals/results
│   └── report.md                # Human-readable, the spec deliverable
└── README.md
```

### 7.3 Runner

`python evals/run.py` imports the same `core/` modules the backend uses (no duplication of logic), runs each dataset through the engine, computes the eval metrics, and writes both `report.json` and `report.md`. CI-friendly — exit code reflects pass/fail.

### 7.4 In-app `/evals` page

The frontend fetches `/api/evals/results`, which reads `evals/results/report.json` from disk and returns it. The page renders pass/fail badges per eval, expandable per-test-case details (input, expected, actual), and a link to download `report.md`. Read-only — no live execution from the browser.

## 9. Design Principles & Tradeoffs

### 9.1 Principles

1. **Determinism in the engine, LLM in the language.** Anything a counselor or recruiter might dispute — scores, rankings, flags — is a pure function. Only narrative is LLM. This is why the three evals are stable.
2. **Explainability is non-negotiable.** Every score, gap, and flag exposes the input signals that produced it. The UI surfaces both signal and LLM line so users see the trail.
3. **Human-in-the-loop for high-stakes outputs.** The at-risk system flags and recommends; counselors decide and act. No auto-messaging students.
4. **Stable evals.** Evals test deterministic logic, not LLM behavior — pass/fail doesn't drift with model version changes.

### 9.2 Tradeoffs

| Decision | What we gained | What we gave up |
|---|---|---|
| FastAPI + React (vs. Streamlit) | Mobile-first responsive UI, polished demo, clean separation of concerns | Two stacks to manage, more boilerplate |
| Live LLM (vs. cached pre-generated) | Demo feels alive, regenerates on data change | API key required at runtime, network dependency |
| Hosted demo (vs. local-only) | Reviewer clicks a link, no setup | Deployment work + backend hosting cost |
| Hardcoded benchmarks (vs. learned from data) | Predictable, explainable, no training data needed | Won't generalize to new tracks without manual configuration |
| In-memory data (vs. DB) | Zero infra, fast | Counselor actions are lost on restart |
| Synthetic data (vs. real Sunstone) | No privacy or access concerns | Eval metrics are only as meaningful as the synthetic profiles |

### 9.3 Explicitly out of scope (Phase 2)

- Real authentication / user management
- Persistent database for counselor actions
- Cluster B features: adaptive content sequencing, AI doubt resolution
- Push notifications / WhatsApp nudges
- Multi-tenant (multiple colleges)
- Counselor action history / audit log

## Appendix: Glossary

- **ELQD** — English, Logic, Quant, Domain. Sunstone's four-dimensional academic framework.
- **Pillar A** — Readiness Score Engine. Numerical score 0–100 with per-dimension breakdown.
- **Pillar B** — Skill Gap Intelligence Layer. Radar chart + top 3 priority gaps.
- **Pillar C** — Early Warning & Counselor Alert System. At-risk flagging + intervention briefs.
- **Career track** — BFSI / Analytics / Digital Marketing. Each defines dimension weights and sub-skill benchmarks.
- **Readiness score** — 0–100, weighted combination of assessment scores (60%), attendance (20%), and engagement signals (20%) across ELQD dimensions, with track-specific weights applied to the dimensions.
- **Gap** — A sub-skill where the student's score is below the track benchmark. Ranked by `gap_size × dimension_weight`.
- **At-risk** — Flagged when `readiness < 55` AND `trajectory_slope ≤ 0` AND `days_to_placement >= 60`.
